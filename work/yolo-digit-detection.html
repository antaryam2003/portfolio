You Only Look Once: real-time digit detection, built from the math up

A project that started in linear algebra and ended in a live camera feed. The useful part wasn’t getting the detector working — it was learning exactly where it stopped working, and realising that deciding what to do about that is a product call, not an ML one.

The context

Stamatics runs mathematics-led projects out of the Department of Mathematics at IIT Kanpur, and this one took the deliberately slow route into deep learning: understand convolution as an operation on matrices first, then build up to a modern detector.

That order matters. It’s entirely possible to get a detector running from a tutorial in an afternoon and understand nothing about why it behaves the way it does. Starting from the linear algebra means that when the model fails — and it does — you have some basis for reasoning about the cause rather than reaching for another hyperparameter.

Starting with the math

We worked through convolutional neural networks properly: what a convolution is doing to a matrix, why weight sharing makes it tractable, how depth builds features from edges up to shapes, and what pooling actually throws away. Then the fundamentals in context — how CNNs are used in the real world and why they displaced hand-engineered features almost entirely.

The thing that stuck: a CNN is a stack of very simple operations, and almost every strange behaviour it exhibits is traceable to something equally simple. A model that fails on rotated digits isn’t mysterious — it’s a model that was never shown rotated digits.

Why YOLO is designed the way it is

Detectors before YOLO essentially ran a classifier repeatedly across an image — accurate, and far too slow for video. YOLO reframes detection as a single regression problem: divide the image into a grid, and in one pass predict bounding boxes, confidence scores and class probabilities together.

That’s a trade, and it’s worth naming plainly. You give up some accuracy — particularly on small and tightly clustered objects — and you buy an enormous amount of speed.

Why I care about this as a product person

“Slightly worse, fast enough to be live” beats “excellent, four seconds later” for anything interactive — and loses badly for anything where a mistake is expensive. The architecture doesn’t tell you which situation you’re in. That call belongs to whoever understands the user.

What I built

  • Worked through CNN fundamentals with the underlying linear algebra, rather than treating the layers as opaque blocks.
  • Analysed the YOLO algorithm’s inner workings — grid assignment, bounding-box regression, confidence scoring and class prediction in a single pass.
  • Developed and integrated YOLO for real-time digit detection, taking it from architecture to a working live pipeline.
  • Evaluated where the detector held up and where it degraded, and traced each failure mode back to a cause in the data or the architecture.

Where it broke, and what that taught me

The failures were more instructive than the successes, and every one of them has a direct analogue in shipping software:

  • Confidence is not correctness. The model was perfectly capable of being wrong with a high score. Any interface that surfaces a confidence number to a user is making a claim it can’t entirely back.
  • Small and overlapping digits suffered. The known cost of YOLO’s grid approach — predictable once you understand the architecture, invisible if you don’t.
  • Distribution shift is the real enemy. Lighting, angle, handwriting style, background clutter. Performance on clean data told me almost nothing about performance on a live feed, which is a lesson about test environments generally.
  • The confidence threshold is a business decision. Raise it and you miss real digits; lower it and you hallucinate them. There is no technically correct answer — only an answer that depends on whether a false positive or a false negative costs you more. I’ve reached for that framing constantly since.

What I’d do differently

  • Build the evaluation set before the model. I assessed performance largely on clean data and discovered the hard cases in the live pipeline. A deliberately adversarial test set — bad light, odd angles, unfamiliar handwriting — assembled first would have redirected the work earlier.
  • Report precision and recall separately, always. A single accuracy figure hides the exact trade-off that anyone deploying the model needs to make.
  • Instrument the failures. Logging every low-confidence frame would have turned a vague sense of “it struggles sometimes” into a ranked list of things to fix.
